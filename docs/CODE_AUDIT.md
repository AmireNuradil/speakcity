## 1. Баги и гонки

### F-01 · high · `WAVEHDR` не закреплён в памяти, пока им владеет драйвер

**Где:** `src/SpeakCity/WavRecorder.cs:39`, `:164-176`, `:206`, `:358-374`.

**Что не так.** Заголовки буферов лежат в обычном управляемом массиве `private WAVEHDR[]? _headers;`. В драйвер они
передаются через `ref`:

```csharp
if (waveInPrepareHeader(_handle, ref _headers[index], HeaderSize) != 0) …   // :172
if (waveInAddBuffer(_handle, ref _headers[index], HeaderSize) != 0) …       // :174
if (waveInAddBuffer(_handle, ref header, HeaderSize) != 0) return;          // :206
```

Marshaller закрепляет элемент только **на время вызова**. Драйвер же хранит указатель на `WAVEHDR` до возврата
буфера и асинхронно пишет туда `dwFlags` (`WHDR_DONE`) и `dwBytesRecorded`. Закреплены только буферы данных (`_pins`),
массив заголовков — нет. После GC со сжатием массив переезжает. Дальше:
1. поток `Drain` проверяет флаги по новому адресу, где `WHDR_DONE` никогда не появится; все 8 буферов, стоящих
   в очереди, пропадают, и запись молча останавливается;
2. драйвер пишет по старому адресу, где уже могут лежать другие объекты, — это порча управляемой кучи.

Кроме того, `waveInUnprepareHeader` вообще не объявлен и не вызывается (0 вхождений), хотя его нужно вызывать до освобождения буферов.

**Доказательства.**
- NAudio в `WaveInBuffer.cs` делает именно то, чего здесь не хватает:
  `hHeader = GCHandle.Alloc(header, GCHandleType.Pinned); // we need to pin the header structure`
  (https://github.com/naudio/NAudio/blob/master/NAudio.WinMM/WaveInBuffer.cs).
- Воспроизведение `/tmp/gcmove`, .NET 10: такой же `WAVEHDR[8]` и такой же паттерн аллокаций, как в `Drain`
  (`new byte[4096]` на буфер плюс `MemoryStream`) в течение 60 с записи:
  ```
  after 60 s of Drain-like allocation: gen0 GCs=1, header array moved=True
  after one compacting gen0 GC: header array moved=True (driver still holds 0x2abeda808f10, array now at 0x2abeda008e18)
  ```

**Риск.** Длинный ответ обрезается где-то посередине, и распознавание «теряет слова». Возможны редкие необъяснимые
падения процесса. Живой тест из `AGENT_STATE.md` длился 3 с и, скорее всего, закончился раньше первого GC,
поэтому проблему не показал.

**Исправление (≈30 строк, малая стоимость).** Выделить 8 заголовков в неуправляемой памяти
(`Marshal.AllocHGlobal(HeaderSize * BufferCount)`) или закрепить массив через `GCHandle.Alloc(_headers, Pinned)`
на всё время записи. P/Invoke перевести на `IntPtr`, флаги читать через `Marshal.ReadInt32`/`Volatile.Read`.
В `Abandon` вызывать `waveInUnprepareHeader` до `pin.Free()`.
Проверка на Windows: запись 25 с с принудительным `GC.Collect()` каждую секунду; длина WAV должна совпасть с длительностью.

### F-10 · medium · нативный Send теряет текст ученика и рассинхронизирует чат

**Где:** `src/SpeakCity/NativeMainWindow.cs:729-761`.

```csharp
AddMessage("You", text);
_input.Clear();                                                             // :738-739, до запроса
var body = new JsonObject { ["text"] = text, ["request_id"] = Guid.NewGuid().ToString("N") }; // :740
…
SetStatus("Send failed: " + FailureText(response, payload));                // :745
```

**Что не так.** При любой ошибке (таймаут провайдера, 429, `session_expired`, `turn_limit`, `dialogue_ended`,
`engine_busy`) пузырь «You» остаётся в чате, хотя сервер реплику не принял, а поле ввода уже пустое. Надиктованный
ответ пропадает, его нужно произносить заново. Каждая попытка получает новый `request_id`, поэтому идемпотентность
роутера (`CompletedTurns`) из нативного окна не используется. Пользователь видит сырые коды вроде
`Send failed: session_expired`. После `session_expired` поле `_sessionId` не сбрасывается, и все следующие Send тоже падают.

**Доказательства.** Код выше. Для сравнения: web UI делает правильно (`ui/app.js:349`
`if (!S.pending || S.pending.text!==text) S.pending={text,request_id:crypto.randomUUID(),…}`), и это закреплено
тестом `turn failures preserve text and request_id…` (проходит, см. таблицу тестов).

**Исправление (малая стоимость).** Пузырь добавлять после успеха (или помечать неотправленным), при ошибке
возвращать текст в `_input`, хранить `request_id` до успеха или до изменения текста, коды переводить в человеческие фразы,
на `session_expired`/`dialogue_ended` сбрасывать `_sessionId`.

### F-11 · medium · запись не глушит голос Люси; нет защиты от устаревшего TTS

**Где:** `src/SpeakCity/NativeMainWindow.cs:254-279` (`ToggleMicrophoneAsync`), `:327-355` (`SpeakAsync`), `:721`, `:751`.

**Что не так.** `_player.Stop()` не вызывается нигде: единственная остановка — `_player.Close()` в `Closing` (`:229`).
TTS запускается fire-and-forget (`_ = SpeakAsync(...)`), и кнопка Speak доступна сразу после ответа, пока голос ещё
синтезируется или играет. У waveIn нет эхоподавления, а у web-рекордера оно включено
(`ui/recorder.js:11` `echoCancellation: true, noiseSuppression: true, autoGainControl: true`). Значит, голос Люси
из колонок попадает в запись ученика, и Whisper расшифровывает его как ответ. В `SpeakAsync` нет счётчика
последовательности, как `speakSeq` в web UI: «Replay» и авто-озвучка, а также запоздавший TTS прошлой реплики
перебивают друг друга.

**Риск.** Мусор в транскрипте, особенно без наушников. Насколько это заметно, нужно проверить на Windows.

**Исправление (малая стоимость).** При старте записи вызывать `_player.Stop()` и повышать счётчик; в `SpeakAsync`
проверять счётчик перед `Open/Play`; пока идёт запись, не начинать воспроизведение.

### F-12 · medium · таймаут worker'а учитывает очередь и каскадно убивает процесс

**Где:** `src/SpeakCity/SpeechWorkerClient.cs:96-98`, `:126-132`; `src/SpeakCity/AppRouter.cs:64-68`.

```csharp
limit.CancelAfter(TimeSpan.FromSeconds(120));
await _serial.WaitAsync(limit.Token).ConfigureAwait(false);   // бюджет тратится и на ожидание очереди
…
catch (OperationCanceledException) { StopProcess(); … throw new TimeoutException(…); }
```

**Что не так.** 120 с отсчитываются с момента постановки в очередь. Запрос, долго стоявший за другим, получает
остаток бюджета, падает по таймауту и **убивает процесс**. Вместе с процессом теряются загруженные Kokoro и Whisper
и кэш отпечатков целостности, поэтому следующий запрос снова платит за холодный старт: перехэширование ~500 МБ
и загрузку моделей. Отдельно: в `/api/bootstrap` результат `_modelsReady = false` кэшируется навсегда после
единственной неудачной попытки ping, и окно советует «Reinstall SPEAKCITY», хотя голос потом может заработать.

**Доказательство (стенд, настоящий `SpeechWorkerClient` + `AppRouter`, заглушка: TTS 110 с, STT 15 с).**
```
E0 worker pid 21431
E1 tts (110 s of work): HTTP 200 at 110.1s
E2 stt queued behind tts (15 s of work): HTTP 504 {"detail":"The local speech component took too long. …"} at 120.3s
E3 second stt queued: HTTP 504 {…took too long…} at 120.5s
E4 worker pid after timeout 23272 (restarted=True) at 120.5s
```
STT, которому самому нужно 15 с, упал на 120-й секунде; следующий запрос из очереди тоже упал; worker перезапущен.
Это **не противоречит** замеру из `AGENT_STATE.md` («зависший worker освобождает gate через 120 с»): gate
действительно освобождается. Проблема в том, что бюджет общий и что таймаут влечёт убийство процесса.

**Риск.** На медленном ПК (HDD, антивирус сканирует DLL PyInstaller) первая связка ping → TTS → STT может уйти
в спираль «таймаут → холодный старт → таймаут». Вероятность — подозрение.

**Исправление (малая стоимость).** Отдельный бюджет на ожидание gate, 120 с отсчитывать после захвата. Процесс
убивать только если запрос уже записан в stdin, иначе вернуть «занято». В `bootstrap` повторять ping, если прошлый результат `false`.

### F-13 · low · утечка временных TTS-файлов

**Где:** `src/SpeakCity/NativeMainWindow.cs:65-66`, `:342-347`, `:357-365`, `:229`.

```csharp
RetireSpokenFile();          // :344 — удаление падает, если плеер ещё держит файл
_spokenFile = path;          // :345 — единственная ссылка на старый файл затёрта
_player.Open(new Uri(path));
```

**Что не так.** `RetireSpokenFile` при `IOException` «оставляет путь для следующей попытки». Но в `SpeakAsync` путь
тут же перезаписывается, так что обещание из комментария (`AGENT_STATE.md` §4b: «the next line retries if it is
still open») кодом не выполняется. `Open` нового файла стоит **после** попытки удаления, а `_player.Close()` перед
удалением не вызывается. При закрытии окна последний файл не удаляется никогда.

**Подозрение (Windows).** Если `MediaPlayer` держит файл открытым и после `MediaEnded` (типичное поведение WPF),
утекает **каждая** реплика, по 0,2–0,6 МБ в `%TEMP%`.

**Исправление (малая стоимость).** Вызывать `_player.Close()` перед удалением; вести список «к удалению» и чистить
`speakcity-tts-*.wav` при старте. Ещё проще — играть WAV из памяти (`System.Media.SoundPlayer(Stream)`), тогда временных файлов нет вовсе.

### F-14 · low · нативное окно не удаляет сессии

**Где:** `src/SpeakCity/NativeMainWindow.cs:698-728` (`StartAsync`), `:809`; `src/SpeakCity/AppRouter.cs:104`.

**Исправление (тривиально):** DELETE предыдущей сессии в `StartAsync` и после успешного `FinishAsync`.

## 2. Задержка хода (Send → текст Люси → голос Люси)

### Как устроен путь сейчас (по коду)

1. `SendAsync` → `AppRouter.HandleAsync`: проход по сессиям для истечения (не больше 32), `session.Gate.WaitAsync(0)` —
   без ожидания, при занятости сразу 409.
2. `TurnAsync` → `CompleteAsync`: `_apiSlot.WaitAsync(0)` тоже **не ждёт**, при занятости сразу `engine_busy`.
   Очереди здесь нет, так что это точка отказа, а не задержки.
3. `ApiClient.CompleteJsonAsync`: один HTTPS POST без стриминга, `response_format=json_object`, `max_tokens=700`,
   `temperature=0.2`, таймаут 90 с на обе попытки (`ApiClient.cs:27`, `:65-69`). Замер из `AGENT_STATE.md`
   для DeepSeek: 1,4–8 с.
4. **Текст показывается до голоса — это правильно** (`NativeMainWindow.cs:750-751`; в web UI то же: `render()` перед `playSpeech`, `ui/app.js:359-360`).
5. `SpeakAsync` → `/api/tts` → `SpeechWorkerClient._serial` (TTS и STT взаимно исключают друг друга; worker
   однопоточный, так что gate отражает его реальную ёмкость) → Kokoro синтезирует **всю** реплику целиком →
   base64 в JSON → временный файл → `MediaPlayer.Open/Play`.

Реальные числа Kokoro и Whisper на ПК владельца отсюда не измерить: модели и Windows недоступны.

### F-08 · medium · прогрев не загружает модели

**Где:** `src/SpeakCity/NativeMainWindow.cs:367-401` плюс комментарий `:368`; `speech/worker.py:324-348`, `:350-353`, `:400-403`.

**Что не так.** Комментарий утверждает: «warms the worker process and model loading before the first turn».
Прогрев на деле — один `/api/bootstrap` → `ping`. А `ping` в worker'е только проверяет целостность файлов:

```python
def ping(self) -> dict:
    tts_ready = self._ready(TTS_ASSETS)   # → _verify_assets → SHA-256 ~500 МБ при первом вызове
    stt_ready = self._ready(STT_ASSETS)
```

`_load_tts` и `_load_stt` (ONNX-сессия Kokoro 325 МБ, eSpeak, импорт onnxruntime / faster_whisper / ctranslate2 / av)
вызываются только из `tts()` и `stt()`. Тест `test_worker_process_is_lazy_without_runtime_imports` прямо закрепляет,
что процесс ленивый. Поэтому **первая** озвучка (приветствие Люси сразу после Start) и **первая** расшифровка
всегда холодные. Если хэширование от прогрева ещё идёт, TTS приветствия ждёт его в очереди.

**Исправление (малая стоимость, worker не трогаем).** После успешного ping отправить `tts` с текстом «Hello.»
и `stt` с 0,5 с тишины (корректный WAV 16 кГц; `vad_filter` вернёт пустой текст, но модель загрузится).
Результаты выбросить. Пока ученик выбирает сценарий, это почти всегда незаметно. Выигрыш нужно измерить на Windows:
время первой озвучки до и после.

### Предложения, которые не являются багами (эффект не измерен)

- **P-1. Озвучка по предложениям.** Протокол worker'а это уже позволяет (несколько `tts`-запросов). Первое
  предложение (5–10 слов) начнёт звучать, не дожидаясь синтеза всех 40 слов. Цена средняя: очередь клипов
  в окне, следующий клип по `MediaEnded`. Хорошо сочетается с F-11 (счётчик последовательности).
- **P-2. Управление reasoning.** `max_tokens` = 700 — это потолок, для моделей без рассуждений лишних затрат он не
  даёт. Если выбранная модель рассуждает, задержку можно срезать параметром OpenRouter
  `reasoning: {"effort": "low"}` или `{"enabled": false}`, если модель это поддерживает (поддержку сообщает
  `GET /api/v1/models`, см. https://openrouter.ai/docs/guides/best-practices/reasoning-tokens). Прежде чем включать,
  нужно измерить, и только для OpenRouter-совместимых базовых URL.
- **P-3. Фидбэк на одном языке.** `FinishAsync(session, ct)` вообще не читает тело запроса, где окно передаёт
  `language`, поэтому модель всегда пишет объяснения на трёх языках (en/kk/ru). Кириллица дорога в токенах.
  Запрос «en + выбранный язык» сократит вывод примерно на треть: ответ станет быстрее, а риск обрезки по 1300 токенам
  (F-06) — ниже. Компромисс: смена языка после отчёта покажет английский.
- **Мелочь.** `WavRecorder.Stop` выполняется в UI-потоке: `JoinPump` ждёт до 250 мс (закрытый event будит поток
  только по таймауту `WaitOne(250)`), плюс синхронный `File.WriteAllBytes`. Это небольшая заминка после «Stop».

### F-03 · high · точное совпадение `original` со всей репликой теряет весь отчёт

**Где:** `src/SpeakCity/AppRouter.cs:171`, `:185`, `:237`, `:241-257`.

**Что не так.** Промпт называет массив «learner sentences», но элементы — это **реплики** длиной до 400 символов,

предложение, опускает финальную точку или меняет `'` на `’`. Такие правки отбрасываются. Если отброшены все,
следует повтор и затем 503: ученик теряет **весь** отчёт, а не одну правку.

**Доказательство (стенд, настоящий `AppRouter`).**

**Риск.** Вероятно, это часть потерь, которые остались после исправления с повтором (15 из 18 правок в `AGENT_STATE.md`).

**Исправление (малая стоимость, ≈20 строк плюс self-test).** Принимать `original`, если после нормализации
(кавычки и апострофы → ASCII, схлопнутые пробелы, отброшенная финальная пунктуация) он совпадает с репликой
**или является её подстрокой**. Главное свойство сохраняется: правка должна опираться на реально сказанный текст,
выдумать `original` модель не сможет. Более строгий вариант: передавать `[{"i":0,"text":…}]` и требовать `index`.

### F-06 · medium · повтор покрывает не все сбои, а диалог уже закрыт

**Где:** `src/SpeakCity/AppRouter.cs:236`, `:247-257`.

**Исправление (малая стоимость).** Один повтор и на исключения «неполного или битого ответа», но не на 401/403/429 и
таймауты; для этого удобно ввести отдельный тип исключения в `ApiClient`. Вместе с P-3 это снижает и риск обрезки.

### F-07 · medium (подозрение) · псевдо-JSON в промпте провоцирует испорченный ключ

- `ApiClient`: повтор строго ограничен (только явный отказ `response_format` или дубли ключей); строгий разбор с
  отказом на дублирующиеся свойства; тексты ошибок провайдера не пробрасываются; один статический `HttpClient`.
- Worker: продуманный протокол (id на каждый ответ, ограниченные строки, ответ даже на битую строку), кэш отпечатков
  целостности вместо хэширования на каждом запросе, ленивые импорты.
- Web UI (`ui/app.js`): повтор хода с тем же `request_id`, сохранение черновика, DELETE старой сессии, защита от
  устаревшего TTS, лимит 29 с, браузерные AEC/NS/AGC. Нативному окну стоит взять эти же решения (F-10, F-11, F-14).
- Сборка: `Copy-Fresh` делает повторный прогон возможным; хэши пинованных загрузок; проверка Authenticode у
  бутстрапера WebView2; Python 3.11 закреплён; gate на лицензии fail-closed.
- `--self-test` делает настоящий цикл Kokoro → Whisper на собранном worker'е, а не только ping.
